ROLES

- Autorizaciones:

ESTADOS DEL PEDIDO
- RECEP: pedidos PICADOS sin iniciar PACKING (Checked=0, no scans).
- CHK: cuando se hace el primer scan (inicia packing).
- CONFIRMADO WMS: cuando se cierra el packing del pedido.
- CONFIRMADO DESPACHO: NO implementar (solo mostrar como estado posible si existiera en seeds, pero no generar flujo).

REGLAS DE CANTIDADES
Cada línea del pedido tiene 3 cantidades:
- OrderedQty (ordenada)
- PickedQty (picada)
- CheckedQty (chequeada por packing) -> se acumula por scans
Meta del packing: alcanzar PickedQty.
Semáforo por línea y por pedido:
- Verde: CheckedQty == PickedQty
- Amarillo: CheckedQty != PickedQty
- Rojo: (PickedQty - CheckedQty) >= 1 o faltante reportado para esa línea
Nota: Si CheckedQty supera PickedQty, es SOBRANTE (incidencia).

ETIQUETAS / BULTOS / CAJAS (equivalentes)
- Un pedido puede tener N etiquetas creadas manualmente “al ojo”.
- Formato labelId: CLIENTE-ORDERID-SEQ (ej: SOLUM-4500123-03)
- Mientras el pedido está abierto, mostrar SEQ/? (no se conoce total). Al cerrar el pedido, congelar y mostrar SEQ/TOTAL.

- Eliminación de etiquetas:
   - Una etiqueta SOLO puede ser eliminada si NO tiene contenido (no tiene scans asignados).
   - Si una etiqueta tiene scans asignados, el sistema DEBE bloquear la eliminación de la etiqueta y mostrar un mensaje indicando que primero se deben eliminar manualmente todos los scans asociados.
   - El sistema NO debe eliminar scans automáticamente al eliminar una etiqueta.
   - La eliminación de scans debe ser una acción explícita del usuario (por registro o en lote, según diseño), respetando reglas de autorización si aplican.
   - Solo cuando una etiqueta queda completamente vacía (sin scans), se debe habilitar la opción “Eliminar etiqueta”.
   - Si existen incidencias asociadas a scans eliminados, dichas incidencias deben mantenerse registradas como histórico (no deben borrarse automáticamente).

- Cerrar etiqueta:
  - Una etiqueta cerrada no permite agregar scans.
  - Se puede reabrir etiqueta con autorización (supervisor/admin 1 click; operario pide clave).
  - Si se reabre y luego se cierra de nuevo, se debe reimprimir SOLO si hubo cambios de contenido desde el último cierre.
- Peso:
  - Cada SKU tiene peso teórico por unidad (en catálogo).
  - El peso teórico de la etiqueta es la suma (pesoSKU * cantidadChecadaRealEnEA).
  - Al cerrar etiqueta simular balanza: mostrar modal “Leyendo balanza…” y asignar un peso real automático cercano al teórico.
  - En ese modal permitir editar el peso real (editable SOLO con autorización si es operario).
  - Si |pesoReal - pesoTeorico| supera un umbral (definir umbral razonable, ej 5% o 0.5kg), generar incidencia DIF_PESO automáticamente.

SCANNER / CHEQUEO
- El usuario puede ingresar SKU o EAN.
- Si se ingresa EAN, mapear a SKU mediante catálogo.
- Si el EAN está duplicado (mapea a más de un SKU), el sistema debe pedir SKU interno manualmente (modal/input).
- Validación principal:
  - TRUEQUE: si el SKU (o combinación SKU+LOTE) no pertenece al pedido, registrar incidencia TRUEQUE y alertar.
  - El sistema asigna automáticamente a qué línea pertenece el SKU escaneado:
    - Si el SKU está en 1 línea => usar esa línea.
    - Si el SKU está en varias líneas => elegir la primera con saldo pendiente (PickedQty - CheckedQty > 0).
- Series:
  - Algunas líneas/SKU requieren series (flag requiresSeries).
  - Si requiere series: el usuario escanea series una por una (cada enter agrega una serie).
  - La cantidad se incrementa automáticamente por cada serie (no editable manualmente).
  - La serie es única global: validar contra todas las series ya registradas en todos los pedidos (en storage). Si serie ya existe, bloquear y alertar.
- Lote:
  - Algunas líneas/SKU requieren lote (flag requiresLot).
  - Flujo: escanear/ingresar lote y luego ingresar cantidad.
- UOM:
  - Cada SKU tiene conversiones por UOM propias, ejemplo:
    - EA:1, PACK6:6, MASTER24:24 (depende del SKU)
  - Permitir seleccionar UOM al ingresar cantidad (solo si NO es por series).
  - Permitir mezclar UOM en el mismo SKU (múltiples scans con UOM diferentes).
  - Siempre acumular CheckedQty en unidad base (EA) para comparaciones y peso.
- Sobrante:
  - Si el usuario intenta registrar cantidad que hará CheckedQty > PickedQty:
    - Mostrar confirmación “¿Seguro?”.
    - Si confirma, permitir registrar pero requerir autorización (según rol).
    - Registrar incidencia SOBRANTE con datos: SKU, QTY, LABEL, USUARIO, FECHA/HORA, AUTORIZADO, COMENTARIO(opcional).
- Faltante:
  - Debe existir un botón “Reportar faltante” por línea.
  - Al presionarlo, crear incidencia FALTANTE con qtyFaltante = PickedQty - CheckedQty (si >0).
  - No requiere autorización.
  - Marcar esa línea en rojo.
- Continuidad:
  - Un pedido puede alternarse (no lock por operario).
  - Al primer scan del pedido, cambiar estado a CHK.

REPACK (MOVER ENTRE ETIQUETAS)
